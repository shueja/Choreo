# Choreo 2026

[Choreo full screenshot]

The SleipnirGroup team of developers is excited to release Choreo for the REBUILT game, Choreo's third season. 

Thanks to @mjansen for the vector field background for REBUILT.

Given the significant changes coming for 2027, Choreo and ChoreoLib look fairly similar to 2025. However, we have added a few major features, fixed many bugs, and made some important changes to avoid issues further down the road.

## Trajectory and Variable Naming Rules
### Character restrictions
To make the below code generation feature possible, and to simplify many aspects of the app, Choreo now requires that trajectory and variable names are valid variable names (identifiers) in C++, Python, and Java. **Valid names can only contain letters (a-z, A-Z), numbers (0-9), and the underscore character (_). They cannot begin with a number.**
> Choreo's code generation will intentionally output errored code if this rule is broken, and the code will have a comment explaining the rule. The Choreo app will indicate any trajectories that need to be renamed.

### Reserved words
* Java keywords are not valid trajectory or variable names.
* There are many predefined terms (mostly units) in the Choreo expression parser (Math.JS), and inadvertently naming a variable one of these could have unexpected and hard-to-reverse consequences. Therefore, **variables cannot be named a Math.JS reserved word.** Choreo will give specific feedback if a name is invalid, but [here](https://mathjs.org/docs/datatypes/units.html#reference) is the list of units and constants for reference. 

> We do recognize that most single-letter names are made invalid by this rule. However, in a name collision between `m` for meters and `m` for a variable, Choreo has to preserve the standard unit abbreviations.

## Java Code Generation
Choreo 2026 can generate Java constants classes containing information about the trajectories and variables in your Choreo project.

See the [docs](https://choreo.autos/usage/code-generation/) for full information and usage examples.

This addresses several limitations and/or opportunities for human error in Choreo 2025:
* Many teams asked for a way to access the defined pose variables from robot code, and several developed systems to parse the .chor file at runtime. While this worked, it could become hard to keep the code up to date with the .chor file.
* Trajectories were loaded by providing the `String` name of the trajectory, but there was no compile-time check to ensure the referenced trajectories actually existed.

In Choreo 2026, two Java files can be generated at a file location of your choosing:
### ChoreoTraj

Choreo can output a Java file listing the name, total time, and blue-alliance start and end poses of each trajectory. Each trajectory is represented as a static constant of the `ChoreoTraj` record. The file is rewritten when the project is loaded, and when paths are generated, renamed, or deleted.

Within the AutoFactory o load an `AutoTrajectory` with a given entry, you can do the following:
```java
import static frc.robot.wherever.ChoreoTraj.*;

AutoRoutine routine = factory.newRoutine("Three Piece");
// Instead of routine.trajectory("StationToReef4"), do:
AutoTrajectory traj = StationToReef4.asAutoTraj(routine);
// The static constants for trajectory segments use the naming scheme
AutoTrajectory firstSegment = StationToReef4$0.asAutoTraj(routine);
```

### ChoreoVars

Choreo can output a Java file containing variables defined in the Choreo GUI. Values will use the Java units library when possible.

### Example:
```java
import frc.robot.wherever.ChoreoVars;

Pose2d pose = ChoreoVars.Poses.myPoseVariable;
Distance length = ChoreoVars.myLengthVariable;
double simpleNumber = ChoreoVars.myNumberVariable;
```


## ChoreoLib

Once Choreo 2026.0.0 fully releases after kickoff, the ChoreoLib vendor dependency can be installed in VSCode's vendordep manager, or with the URL `https://choreo.autos/lib/ChoreoLib2026.json`.

The WPILib team has graciously allowed us to host our ChoreoLib releases on the WPILib Maven repositories. This has little impact to the user, but helps us make our release process more automated and future-proof.

### All

* DifferentialSample is updated to add an `alpha` parameter (see the section on schema changes). This is **BREAKING** for code that constructs DifferentialSamples directly.

* For both SwerveSamples and DifferentialSamples, interpolation now integrates the acceleration instead of linearly interpolating all elements of the state.
### Java
* `AutoRoutine`
  * Removed the deprecated method. Use `anyDoneDelayed`.
```java
@Deprecated(forRemoval = true, since = "2025")
  public Trigger anyDone(
      int cyclesToDelay, AutoTrajectory trajectory, AutoTrajectory... trajectories)
```
* `AutoChooser`
  * An `AutoChooser(String doNothingName)` has been added. Use this to change the option name for the default, do-nothing auto.
  * `AutoChooser.addCmd(...)` and `AutoChooser.addRoutine(...)` now return the `AutoChooser` instance for easy chaining.
* `AutoFactory`
  * `AutoFactory.resetOdometry(Supplier<Optional<Pose2d>> pose)` and `AutoFactory.resetOdometry(Optional<Pose2d> pose, boolean doFlipForAlliance)` have been added. They return Commands that use the `resetOdometry` and alliance flipping functionality passed to the `AutoFactory`.
* `AutoTrajectory`
  * Removed the deprecated method 
```java
@Deprecated(forRemoval = true, since = "2025")
public Trigger done(int cycles) {
    return doneDelayed(0.02 * cycles);
}
```
  * The no-arguments `done()` method is still available.
* `ChoreoAllianceFlipUtil`
  * Improved the memory performance of `Supplier<Optional<Pose2d>> optionalFlippedPose2d(...)` and `Supplier<Optional<Translation2d>> optionalFlippedTranslation2d(...)` when they will always return empty Optionals.
### C++
* Removed the deprecated `kTrajSpecVersion` in `util/TrajSchemaVersion.h`. Use `kTrajSchemaVersion`.
### Python
* Added FMS Usage Reporting for ChoreoTrajectory


## Choreo CLI
* An issue that would cause waypoint heading expressions to be reset to their equivalent value in radians has been fixed.
> Known issue: The Choreo CLI does not currently update the generated Java list of trajectories. We aim to fix this within the first 2 weeks of the season.

## Choreo GUI/Generator
### Path Menu
* Changes to robot config are now considered when marking paths out of date. If robot config is changed, all paths will be marked out of date. If robot config is changed back, the paths will be marked up to date again, just like how trajectory parameters work.
* The icon next to each path now shows a saving progress indicator when the file is being saved.
* Path renaming inputs will display an error message if the name is invalid (see above).
* Generate All and Generate All Outdated buttons are added. These will generate all relevant trajectories, but will only process a limited number of trajectories in parallel at one time for performance.

### Variables Menu
* We have code in progress to move the variables to a panel below the field, but this feature is not included in the 2026.0.0 release.
* Variable renaming inputs will display an error message on hover if the name is invalid (see above).

### Code Generation
* The settings for code generation are in Document Settings, in a tab alongside Robot Config.
